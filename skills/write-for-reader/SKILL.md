# 为读者写清楚

读者只会看到交到手里的成品。他们看不到写作者读过的全部对话、文件和调查过程，
也不该先学习一套写作框架。写作时，从读者已经知道、亲自经历或正在关心的事情起笔，
再逐步加入事实、概念、理由和结论。选择场景和检查成品的过程留在内部。

## 写之前先弄清四件事

从用户的请求、对话历史和已有材料中判断：

1. 谁会阅读。
2. 读者亲自经历过什么，已经知道什么，哪些内部名称没有理由知道。
3. 读完以后，读者需要理解什么、判断什么或完成什么。
4. 成品会出现在哪种载体，其中有哪些篇幅、引用或视觉限制。

现有信息足够时直接写。只有两种理解都说得通，而且会产生明显不同的成品时，
才问一个具体问题。例如：“这份材料是给开发者继续排查，还是给负责人决定是否暂停上线？”
不要让用户先理解写作术语再作选择。

同一份成品继续修改时，沿用已经确认的读者和用途，除非用户改变了目标。

## 选择当前场景

选择最接近当前任务的一行，完整读取对应文件：

| 主要任务 | 读取文件 |
|---|---|
| 帮助陌生读者理解概念、错误或复杂过程 | `profiles/explanation.md` |
| 调查系统、事故、数据异常或技术原因 | `profiles/investigation.md` |
| 写论文、研究报告、摘要或同行材料 | `profiles/academic.md` |
| 制作 PPT、演讲稿或页面式汇报 | `profiles/presentation.md` |
| 写邮件、决策材料、项目报告或工作文档 | `profiles/workplace.md` |
| 写故事、品牌内容或其他创意文字 | `profiles/creative.md` |

通常只读取一个场景文件。一份成品确实需要完成两种任务时，可以再读取一个：
主要场景决定整体顺序，次要场景只补充必要要求。例如，学术会议报告用
`presentation.md` 安排页面，再用 `academic.md` 检查证据和术语。

长文、高风险内容、严格重写，或者用户已经指出成品难读时，再读取 `AUDIT.md`。普通短答无需加载。

## 让读者先认识对象

- 从读者做过、看见或问过的事情开始。独立发布的成品没有这类共同经历时，先交代当前对象和写作目的。
- 开头可以给结论，但结论只能使用读者已经知道或当场解释的名称。
- 项目独有的名称第一次出现时，先说明它做什么，以及为什么此处需要提到它。只解释后文真正会用到的部分。
- 背景放在依赖它的内容之前。只有会帮助读者理解、判断或行动的背景才进入正文。
- 比方只帮助理解一个局部关系。先说真实对象，再使用比方；解释完成后，用真实名称复述，并让比方退出后续的因果和结论。

## 把过程和理由接起来

- 先介绍对象，再说明对象之间的关系。写异常时，先让读者知道正常情况下会发生什么。
- 点名谁做了什么、作用于什么、结果影响谁。同一对象保持同一个名称，代词要有唯一指向。
- 叙述过程时，一步推进一个主要变化。多个变化挤在一句话里时，按照发生顺序拆开。
- 解释原因时，写出触发条件、中间发生的变化和最终后果。时间接近、同时发生、相关条件和直接原因分别陈述。
- 判断后面紧跟依据。直接观察、材料记载、受控实验、合理推断和仍然未知的内容，要让读者看得出差别。

## 让读者看出每段话为何出现

- 每段回答一个当前问题。背景靠近它解释的对象，证据靠近它支持的判断。正文无需另行介绍作者的安排。
- 建议要接在目标、限制和原因之后。读者应能看出建议解决什么问题，以及它为什么可能改变结果。
- 标题直接说明这一节的对象、事件、发现或决定。正文使用常见词和具体动词，不用“最关键”替内容分级，也不先反驳读者没有提出的观点。
- “但、却、仍然”等词只用于修正前文已经形成的预期。场景改变时，先写清新内容与前文的关系。
- 简洁只删除重复、绕行和无关内容。理解结论所需的背景、条件、限制和风险继续保留。

## 交付前读一遍

确认下面四件事：

1. 每个新名称出现时，读者都知道它为何进入当前内容。
2. 读者能够沿着明确的对象、动作和时间顺序复述过程。
3. 每项判断都能找到附近的依据，语气没有超过材料支持的范围。
4. 标题和正文都在讲实际内容。场景选择、规则名称、加载过程和自我评价仍留在内部。

用户已经给出的表达偏好继续生效。领域 Skill 可以补充术语、引用和格式要求，但不能覆盖用户的明确要求。

机器读取的内容保持原有语法。逐字引用、转录、正式翻译和强制模板优先保证忠实；需要解释时，把解释与原文分开。
