# write-for-reader

为当前读者完成当前沟通任务。每次运行重新判断场景；同一成品的连续修改沿用已经确认的读者和用途。

## 1. 在内部完成四项判断

从 user 的请求、对话历史、已有材料和成品类型中判断：

1. 谁会阅读。
2. 读者已经知道什么，哪些内容没有理由知道。
3. 读完后需要理解、判断或完成什么。
4. 内容通过什么载体呈现，以及载体的篇幅、结构、引用和视觉限制。

不要展示判断表，不要让 user 重复提供上下文。只有两种合理理解会产生明显不同的成品，并且现有材料无法排除其中一种时，才问一个描述实际差别的问题。

## 2. 只加载当前需要的场景文件

选择一个主要场景，并完整读取对应文件：

| 主要任务 | 读取文件 |
|---|---|
| 帮助陌生读者理解概念、错误或复杂过程 | `profiles/explanation.md` |
| 调查系统、事故、数据异常或技术原因 | `profiles/investigation.md` |
| 写论文、研究报告、摘要或同行材料 | `profiles/academic.md` |
| 制作 PPT、演讲稿或页面式汇报 | `profiles/presentation.md` |
| 写邮件、决策材料、项目报告或工作文档 | `profiles/workplace.md` |
| 写故事、品牌内容或其他创意文本 | `profiles/creative.md` |

默认只读一个 profile。成品确实横跨两种场景时再读第二个：用主要 profile 决定结构，用次要 profile 补充领域要求。不要为求完整加载其余文件。

长文、高风险内容、用户要求严格审稿，或此前已经指出文字难读时，再读取 `AUDIT.md`。普通短答不加载。

## 3. 所有场景共同保留

- 从读者已经知道或亲自经历的事情开始。新概念先交代为何进入当前内容，再按需要解释。
- 每段只服务一个明确问题或任务。通过内容顺序和前后连接体现它的作用；不要另写一句说明作者为什么安排这一段。
- 按信息依赖安排顺序。后文使用的对象、前提和事件先在前文出现。
- 点名谁做了什么以及影响谁。代词只能指向一个对象；同一对象全篇使用同一个名称。
- 事件叙述一次推进一个主要状态变化。因果说明包含触发条件、中间变化和后果；区分先后、同时、相关条件和直接原因。
- 让主张与证据强度一致。直接观察、材料记载、合理推断和未知内容能够被读者区分。
- 建议从当前目标、限制条件和前文已经说明的原因推出。让读者看出它解决什么问题，以及为什么可能改变结果。
- 使用常见、准确的词和具体动词。标题陈述内容；正文删除作者自我评价、口号、虚构对立和无依据的强调。
- 切换场景时写清它与前文的关系。“但、却、仍然”等转折只修正前文已经形成的真实预期。
- 保留理解、判断或行动所需的背景、条件、限制和风险。简洁只减少重复、绕行和无关内容。
- user 已经给出的个人表达偏好持续生效。领域 Skill 可以补充结构、术语和引用规范。

## 4. 交付成品

按选定 profile 写作。内部判断、规则名称、加载过程和检查记录不进入正文。

开头可以先给结论，但只能使用读者已经知道或当场解释的概念。使用比方前先点明真实对象；一个比方只解释一个局部关系；解释完成后用真实名称复述，并让喻体退出后续因果、判断和结论。

机器读取的内容保持其语法。逐字引用、转录、正式翻译和强制模板优先保证忠实，解释与原文分开。
