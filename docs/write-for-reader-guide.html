这份说明源于一次具体的修改经历。原稿要解释程序后台的启动异常，却在开头集中放入 Worker、任务边界、重复收尾等内部概念。读者还不知道事情怎样发生，文章已经给出了压缩后的调查结论。

从原稿开始

这段开头让读者在哪里跟丢

事情发生在一个科研软件里。用户打开项目后，发现原先启动的后台仍在提供服务，准备接手的新后台却迟迟没有接管。用户想知道环境准备和数据摸排是否互相干扰，也想知道后台为什么会退出。

读者当时掌握的信息

页面上同时出现了旧后台仍在服务、新后台尚未接管、数据摸排被打断等现象。至于后台由谁启动、怎样交接、任务失败后由谁处理，读者尚未得到解释。

原稿一开头写道：

先说最重要的结论：原事故不是“环境准备太慢，所以后台被迫关闭”。真正让后台退出的是，一项数据 Worker 的失败被两个模块重复收尾，第二次收尾产生内部冲突，错误随后逃出了任务边界，带走了整个后台。

这段话对已经完成调查的人很紧凑。第一次接触事情的人会连续遇到四个障碍：

  1. 开头先纠正一个观点。读者未必认定“环境准备太慢导致后台关闭”，却要先处理这场没有交代来源的争论。
  2. 五个概念同时出现。Worker、模块、收尾、任务边界和后台都没有说明，它们之间的关系也没有出现。
  3. 六个动作被压成一句话。任务怎样失败、两个模块为何都来处理、第二个错误为何没有被接住，都留给读者补全。
  4. 强调先于证据。“最重要”“真正”等词已经替读者作出判断，支持这些判断的日志、代码和实验还在后文。
先补背景，再说明当前发现

用户进入项目后，页面仍然连接着此前启动的后台。系统同时在准备一套新的运行环境；新环境准备完成后，后续请求才会交给新启动的后台。因此，页面在一段时间内会同时涉及前后两套后台。

日志显示，此次退出发生在一项数据任务失败之后。负责调度任务的模块先把任务标记为结束，另一个模块随后又处理了同一个结束动作。第二次处理产生了新的错误。任务执行代码没有接住这个错误，后台进程随之退出。

改写后的文字更长，却减少了猜测。每个新对象都有来由，动作按发生顺序出现，读者也能指出哪些句子来自页面现象，哪些句子来自调查证据。

背景与概念

概念为什么像从半空出现

AI 写作时通常已经看过对话、代码、日志和调查记录。它容易从自己已经形成的完整理解开始写。读者只看到最后的文章，没有经历前面的调查过程。

这会形成一种知识差。作者觉得“后台”“Worker”“任务边界”已经反复出现，读者却可能第一次见到这些词。一个陌生词尚可暂时记住；多个陌生词同时进入一句话时，读者还要猜它们的层级和关系。

新概念进入文章前需要三个落点

  1. 它是什么。后台是一个持续运行的程序进程；Worker 是这个进程里执行具体任务的工作单元。
  2. 它为什么此时出现。文章正在解释一次任务失败如何影响整个后台，因此需要介绍任务与后台的关系。
  3. 后文要用它说明什么。读者随后会看到任务内部的错误怎样越过原有处理范围，影响后台进程。

解释多少取决于读者已有的知识。写给同一项目的开发者，可以省略通用的进程概念；当前事故里特有的模块分工和交接顺序仍要说明。写给首次接触产品的人，则应从页面现象和用户操作开始。

概念先出现

第二套后台未接管时，数据 Worker 已越过环境准入并触发异常收尾。

经历先出现

用户打开项目后，页面仍连接着此前启动的后台。与此同时，系统开始准备新的运行环境。数据摸排任务在这段准备期间启动了。

后一句仍然会继续解释环境、数据任务和两套后台的关系。第一句只承担一个任务：把读者带到事情发生的现场。

动作与因果

一句话省略了哪些动作

“重复收尾导致错误逃逸”听起来像一个完整原因，实际把多个参与者和多次状态变化折叠在了抽象名词里。读者能记住结论，却难以复述发生过程。

把原句展开后，可以看到六个连续动作：

  1. 数据任务报告失败。
  2. 负责调度任务的模块把任务标记为结束。
  3. 另一个模块再次尝试结束同一个任务。
  4. 第二次操作发现任务已经结束，于是产生新的错误。
  5. 任务执行代码没有在自己的范围内处理这个新错误。
  6. 错误继续向外传播，最终使后台进程退出。

展开动作有两个作用。第一，读者能检查每一步是否有日志或代码支持。第二，解决方案有了明确落点：系统可以让结束动作允许重复调用，也可以规定只有一个模块负责结束任务，还可以在任务边界接住第二次操作产生的错误。

代词会进一步隐藏参与者

一句话里同时出现任务、模块、错误和后台时，“它”“这个问题”“该过程”都可能指向多个对象。重复名称看起来略显笨拙，却能避免读者回头猜指向。技术说明中，稳定的对象名称通常比表面上的词语变化更重要。

抽象名词承担过程

重复收尾造成异常逃逸，并触发后台替换。

参与者承担动作

调度模块已经结束任务后，任务管理模块又执行了一次结束操作。第二次操作报错，后台进程随后退出。编排程序检测到退出后，才启动替代后台。

证据范围

哪些判断超过了现有材料

流畅的叙述很容易把观察、代码规则、实验结果和作者推断写成同一种确定语气。读者随后难以判断哪些内容可以直接核查，哪些内容仍可能被新证据推翻。

内容来源可以怎样写需要保留的边界
日志与页面记录在某个时间发生了什么，哪个进程退出，页面显示了什么日志未记录的动机和分支不能自动补全
当前代码满足某个条件时，程序会执行哪条路径代码规则不等于事故当时一定走过这条路径
受控实验在给定顺序和条件下，可以复现什么现象一次复现不能覆盖尚未测试的顺序和环境
综合推断哪些事实共同支持某种解释应说明替代解释以及仍缺少的记录

事故记录里缺少“为什么决定替换后台”这条日志。因此，可以确认后台曾经退出，也可以从代码中找到触发替换的条件；单凭现有记录，还不能确定事故当时究竟是哪一个判断启动了第二套后台。

强调词会放大这个问题。“核心”“本质”“最关键”“已经证明”让推断听起来更加确定，却没有增加证据。需要说明事情重要时，应写出具体后果，例如用户请求被哪套后台处理、项目状态是否可能丢失、后续调查缺少哪条记录。

把一次实验扩大成普遍结论

真实客户端实验已经证明退出阶段存在必然的后台重生问题。

结论停在实验覆盖范围

在这次实验采用的退出顺序下，桌面应用关闭后又启动了一套后台。该顺序可以触发现象；其他退出顺序尚未测试。

标题与语气

标题和句式怎样把注意力带离内容

有些句子没有增加事实，却持续提醒读者作者正在分析、分类或纠正。文章因此像一场由作者主持的汇报，事件本身退到了后面。

原来的写法读者遇到的阻力可以改成
我们不是从代码名词出发，而是连续回答你提出的六个问题标题描述写作方法，没有说六个问题涉及什么事情项目启动后，为什么会同时出现两套后台
从表象追到本质作者先评价分析深度，读者仍不知道本节讨论哪个现象后台退出前发生了哪些动作
先说最重要的结论读者被要求先接受重要性判断，结论中的概念还未介绍直接写结论；若背景不足，先补两句背景
A 不是……而是 B每段都先制造一项对立，读者需要处理自己未必持有的观点说明现有证据支持 B 的哪些部分，以及 A 缺少什么条件

句子节奏也会暴露模板。连续使用否定、转折和三段排比，文章会反复响起同一种拍子。长句若塞入多个动作，读者要等到句尾才知道主干；短句若像日志条目一样并排，动作之间的关系仍然缺失。

修改时应先确认一句话要完成什么，再调整词语。句子需要交代动作，就让执行者靠近动词；需要说明限制，就把条件和结论放在相邻句子；没有增加对象、证据、条件或后果的总结句，可以直接删除。

页面形式

页面怎样帮助阅读，又怎样打断阅读

上一版页面把七类问题分别放进诊断框，每个框又包含症状卡片、对比例子和修正卡片。正文区域一共出现二十多个卡片式块。读者虽然能快速扫到许多标签，却很难连续读完一条解释。

首页也占用了接近一屏的深色区域。标题提出“AI 的文字为什么让人不舒服”，范围远大于页面实际分析的材料；下面的说明又先列出八个抽象类别。读者在看到第一个例子以前，已经读过一段制作说明和三条页面元数据。

这一版采用了更简单的分工：

  • 连续因果使用正文和编号步骤，避免每一步单独装进卡片。
  • 只有两个写法需要横向比较时，才使用并排区域。
  • 表格只比较同一组维度，例如证据来源、表达范围和限制。
  • 流程图和任务示意图放在附录，因为它们解释 Skill 的使用方式，不属于正文论证。
  • 颜色只区分示例、提醒和交互点，不负责替文章宣布严重程度。

页面设计无法补上缺失的背景和因果。视觉形式应表达已经明确的关系：比较用对齐，时间变化用时间线，分支用流程图，连续解释保留连续段落。

形成原因

这些写法为什么容易反复出现

下面的解释用于指导写作和 Skill 设计。它来自对成品模式的归纳，没有直接测量模型内部每一步计算，因此应看作工作解释。

AI 掌握的背景多于读者

模型在写作前读过大量材料，容易把刚刚获得的信息当作共同知识。最终结论离它很近，读者的最初问题反而容易被遗忘。

局部流畅比全篇依赖更容易形成

每句话可以单独通顺，章节之间仍可能缺少前提。模型若没有先安排概念和证据的出现顺序，后文会频繁依赖尚未介绍的内容。

常见文章模板提供了现成外形

结论预告、三段并列、否定后转折和口号式收尾能够快速产生完整文章的样子。它们在某些场合有效，连续重复时会遮住内容本身的节奏。

“专业、全面、有深度”容易被翻译成可见装饰

抽象名词、强烈判断、分层标题和大量卡片都能制造正式感。若任务没有同时规定读者、证据边界和读后任务，模型可能优先满足这种外观。

压缩经常删错位置

背景、条件和中间动作被删掉，作者预告、强调语和重复总结却被保留。字数减少以后，原本写在纸面上的推理工作转移给了读者。

修改方法

一篇文章可以按什么顺序修改

先改句子通常收效有限。背景和证据尚未整理时，润色只会让原有跳跃读起来更加顺滑。下面的顺序适用于技术说明，也可以用于研究报告、论文、PPT 文稿和工作邮件。

  1. 写下读者的起点。读者亲自见过什么，已经读过什么，没有理由知道什么，读完后要理解或完成什么。
  2. 分开事实、代码规则、实验、推断和未知。先确定每项材料能支持到哪里，再决定使用多强的语气。
  3. 安排概念和前提的出现顺序。每一节回答一个具体问题。后文需要的对象，应在前文得到介绍。
  4. 展开关键动作。写清谁做了什么、对象怎样变化、下一步为何发生。多个主要动作不要挤在一句话里。
  5. 处理标题和作者语气。标题说明实际内容。删除没有证据支撑的强调、虚构对立、深度预告和重复总结。
  6. 最后调整句子和页面。用具体动词替换抽象名词，检查代词指向，再决定哪些关系确实需要表格、图或卡片。

附录三

Skill 文件怎样按需加载

主文件保存各场景共同使用的要求。六份场景文件只在对应任务中进入上下文，从而减少无关规则互相干扰。

文件结构

write-for-reader/
├── SKILL.md
├── AUDIT.md
└── profiles/
    ├── explanation.md
    ├── investigation.md
    ├── academic.md
    ├── presentation.md
    ├── workplace.md
    └── creative.md

加载方式

  • 普通任务加载主文件和一份场景文件。
  • 混合任务可以增加一份次要场景文件，由主要场景决定结构。
  • 长文或高风险任务再加载 AUDIT.md。
  • 所有场景文件不会同时加载。

例如，学术会议汇报以 presentation.md 安排页面，再由 academic.md 补充证据和术语要求。普通工作邮件只需 workplace.md。
